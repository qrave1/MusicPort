# MusicPort — план MVP

Дата исследования: 23 октября 2026. Статус: план, реализация и тесты ещё не выполнялись.

Обновление реализации: добавлены CLI, SQLite-индекс, проверка SHA-256, journal pending для восстановления опубликованных файлов, межпроцессная блокировка, Spotify PKCE/keyring, чтение коллекций и стабильного снимка плейлиста, TUI запуска/прогресса/повтора, minimock и CI Windows/Linux. Unit- и интеграционные тесты проходят; покрытие syncer 100%, download 88,6%. Исходная строка статуса выше относится к моменту составления плана.

Осталось: реальная ручная проверка Spotify OAuth, сохранение состава коллекций и M3U8, выбор папки/коллекций в TUI, полноценные jobs с историей ошибок и retry аудиозагрузок, расширение unit-покрытия OAuth/TUI и проверка уязвимостей. Текущие ограничения и команды запуска описаны в README.md.

Решение пользователя: Spotify предоставляет список коллекции; аудиофайлы поступают из отдельного источника с разрешённым скачиванием. Конкретный внешний каталог пока не выбран.

## Объём первой версии

Go-приложение для Windows с TUI. Импорт Liked Songs и выбранных доступных плейлистов, локальный индекс SQLite, скачивание только отсутствующих файлов, повтор ошибок после перезапуска. Одна физическая копия файла может использоваться несколькими плейлистами. Экспорт плейлистов в M3U8 сохраняет порядок и повторные вхождения.


Сохранённые альбомы с разворачиванием треков — следующий этап. Подкасты, аудиокниги, перекодирование, акустические отпечатки, автоматическое удаление файлов и сложное редактирование тегов не входят в первую версию.

## Проверенные ограничения Spotify

- В Development Mode владелец приложения должен иметь Premium; до пяти авторизованных пользователей. Проверить доступ до разработки интерфейса. [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes).
- В 2026 году изменились endpoints и JSON плейлистов: tracks заменяется на items, чтение содержимого чужих плейлистов ограничено. Нельзя обещать импорт любого подписанного плейлиста. [Изменения февраля](https://developer.spotify.com/documentation/web-api/references/changes/february-2026).
- external_ids для треков сохранён после мартовского пересмотра; ISRC использовать как необязательный сигнал. [Изменения марта](https://developer.spotify.com/documentation/web-api/references/changes/march-2026).
- OAuth Authorization Code + PKCE подходит для локального приложения без встроенного client_secret. Использовать state, loopback callback на 127.0.0.1 и зарегистрированный redirect URI. [PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow).
- Различать временный rate limit и исчерпанную квоту. Учитывать Retry-After, ограничивать число повторов; QUOTA_EXCEEDED показывать пользователю, не повторять бесконечно. [Rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits), [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes).

## Архитектура

```text
Spotify → Catalog → Sync planner ← SQLite
                         ↓
                    AudioSource
                         ↓
                Download worker → files
                         ↓
                  события → TUI
```

Каталожный адаптер читает коллекцию; AudioSource сопоставляет трек с файлом; planner решает, что нужно скачать; downloader сохраняет файл; TUI отображает события. Headless-режим использует те же сервисы и нужен для автоматического тестирования.


## Индекс и дубликаты

| Таблица | Назначение |
|---|---|
| tracks | spotify_id PRIMARY KEY, название, исполнители, длительность, ISRC nullable |
| collections | идентификатор, тип, имя, snapshot_id, время успешного сканирования |
| collection_items | collection_id + позиция, spotify_id; повторные позиции сохраняются |
| sources | provider + source_id UNIQUE, format, связь с файловым объектом |
| track_sources | связь Spotify-трека с подтверждённым источником, способ сопоставления |
| files | SHA-256 UNIQUE, относительный путь UNIQUE, размер, mtime, время проверки |
| jobs | source_id + профиль качества UNIQUE, статус, попытки, ошибка, staging_path, ожидаемый хеш |
| sync_runs | начало, завершение, результат сканирования |

Правила:

1. Одинаковый spotify_id в разных плейлистах — одна запись трека, несколько вхождений.
2. Одинаковый provider/source_id и профиль качества — одна задача загрузки. Временный URL не является идентификатором файла.
3. Разные ссылки с одинаковым SHA-256 после скачивания — один физический файл. Без известного хеша/идентификатора заранее исключить такую повторную передачу нельзя.
4. Одинаковый ISRC — кандидат на объединение, а не безусловный UNIQUE. Учитывать длительность и версии; live, remix, remaster, clean/explicit не склеивать автоматически.
5. Название и исполнитель сами по себе не дают надёжного совпадения. Неоднозначные варианты показывать как unresolved.
6. SHA-256 выявляет одинаковые байты. Разные кодеки или теги одной записи могут давать разные хеши; аудиодедупликацию по отпечаткам отложить.

## Алгоритм синхронизации

1. Прочитать локальное состояние и восстановить незавершённые jobs. Одновременную синхронизацию второго процесса отклонять через блокировку/аренду в БД.
2. Получить коллекции с пагинацией. Для плейлистов использовать snapshot_id, когда доступен; подтверждать стабильность снимка после чтения. Liked Songs для MVP сканировать полностью: не считать последнюю дату надёжным курсором изменений.
3. Записывать состав коллекции через staging и транзакцию после успешного полного чтения. Ошибка на второй странице не должна выглядеть как удаление остальных треков.
4. Построить diff: present / new / missing / unresolved / failed. Наличие строки в БД недостаточно: проверить существование и размер файла; при изменившихся размере/mtime пересчитать хеш, отдельный verify проверяет все хеши.
5. Разрешить источник, затем сформировать уникальные jobs. На первый MVP достаточно одного download worker, позже добавить 2–4.
6. Скачать в .part на том же диске, проверить HTTP-статус, ожидаемую длину и хеш при наличии; отклонять HTML-страницы вместо аудио. Предусмотреть таймауты и отмену.
7. Посчитать SHA-256, сохранить его и план финализации в БД, закрыть файл, переименовать, затем отметить done. БД и файловая система не имеют общей транзакции: при запуске сверять staging и финальный файл и завершать прерванную финализацию без повторной загрузки.
8. Хранить файлы по стабильному ключу, например audio/<sha256>.mp3, а читаемые названия — в M3U8 и индексе. Это исключает коллизии имён и лишние копии между плейлистами.
9. Удаление трека из Spotify обновляет состав коллекции, но не удаляет локальный файл. Удаление уже имеющихся пользовательских дублей не выполнять автоматически.

В MVP прерванный .part можно скачивать заново; уже завершённые файлы сохраняются. Побайтовый resume через Range/If-Range и ETag — отдельное улучшение.

## Этапы и результаты

Оценка для одного разработчика: 4–6 рабочих дней при доступном Spotify API и готовых прямых ссылках; интеграция внешнего каталога оценивается отдельно.

1. Проверка доступов и зависимостей — 0,5 дня. PKCE-вход, чтение Liked Songs и одного собственного плейлиста с пагинацией, загрузка одного разрешённого файла, пробная сборка TUI+SQLite. Результат: подтверждены самые рискованные интеграции.
2. Индекс и planner — 1 день. Миграции, уникальность, состав коллекций, dry-run, тест повторного запуска. Результат: корректный список только необходимых загрузок.
4. TUI — 0,5–1 дня. Выбор коллекций и папки, предварительный diff, запуск, прогресс, причины ошибок, повтор failed, выход с сохранением состояния. Сетевые запросы не блокируют Update/View.

## Unit-тесты с minimock — обязательная часть реализации

Тесты писать вместе с каждым этапом, начиная с planner; не переносить unit-покрытие на финальную приёмку. Использовать minimock v3 как единственный генератор моков, без testify/mock и gomock. Чистые функции проверять напрямую табличными тестами, без моков.

Узкие интерфейсы объявлять на стороне потребителя и передавать через конструкторы. Не создавать интерфейс для каждого типа. Предлагаемые границы для minimock:

| Потребитель | Мокируемые зависимости | Что проверяем |
|---|---|---|
| Sync service | Catalog, CollectionStore, SourceResolver, JobStore, Downloader | Полный импорт, diff, отсутствие лишних загрузок, ошибки каждого шага, отмена |
| Download worker | SourceOpener, FileStore, JobStore | Обрыв потока, ошибка записи/закрытия/переименования, неверный хеш, переходы состояний |
| Восстановление | FileStore, JobStore | Сбой до/после rename, готовый файл без done, повторная финализация |
| OAuth service | TokenStore, TokenRefresher | Refresh, ошибка хранилища, отмена, сохранение обновлённого токена |
| Retry policy | Инъекция Now и Wait(ctx, delay) | Retry-After, лимит попыток, отмена ожидания без настоящего sleep |
| TUI model | SyncRunner | Команда запуска, прогресс, ошибки, повтор, запрет второго запуска, отмена |

Названия интерфейсов предварительные. CollectionStore должен предоставлять атомарную замену полного снимка, а не заставлять сервис управлять деталями SQL-транзакции. FileStore описывает нужные файловые операции; не оборачивать всю стандартную библиотеку. Успешное чтение потока можно задавать через bytes.Reader, ошибку чтения — небольшим тестовым reader.

### Обязательные unit-сценарии

- Planner: пустая коллекция; одинаковый трек в нескольких коллекциях; разные Spotify ID с одним source_id; новое качество; существующий и пропавший файл; unresolved; одинаковый ISRC с разными версиями; смена URL при прежнем source_id.
- Sync: ошибка следующей страницы не вызывает замену снимка; изменившийся snapshot не публикует смешанный состав; готовые файлы не вызывают Downloader; три новых источника дают ровно три загрузки; ошибка одного файла отражается в результате и не теряет остальные jobs.
- Worker: done разрешён только после успешной проверки и финализации; ошибки чтения, записи, закрытия, rename и сохранения статуса; неверные размер/хеш; отмена до и во время загрузки; одинаковый хеш привязывается к существующему файлу.
- Recovery: финальный файл существует и совпадает по хешу — завершить job без сетевого вызова; повреждённый файл не становится done; повтор восстановления идемпотентен; .part обрабатывается по политике MVP.
- Retry/auth: временная ошибка и успех, исчерпание попыток, постоянная ошибка, QUOTA_EXCEEDED без повторов, отменённый context, неудачный refresh. Разбор реальных HTTP-ответов дополнительно проверяется через httptest.
- TUI: переходы состояний и команды тестируются без реального терминала; resize и отсутствие зависания отдельно проверяются при ручной приёмке.

В каждом table-driven subtest создавать собственный minimock.Controller и набор моков. Проверять результат и значимые взаимодействия: аргументы, число вызовов, отсутствие побочных эффектов при ошибке. Не ограничиваться проверкой того, что моки были вызваны. Не фиксировать порядок независимых операций; порядок проверки файла, rename и done проверять, поскольку он влияет на сохранность данных.

Для конкурентных тестов использовать каналы/барьеры и явное завершение worker перед проверкой моков; не ждать случайное число миллисекунд. t.Parallel применять только при полностью независимых моках, данных и ресурсах. Проверять передачу cancellation через context, а не только совпадение его экземпляра.

### Генерация и CI

- Зафиксировать версию minimock и генератора из того же модуля в go.mod/go.sum. Для Go 1.24+ закрепить генератор через tool directive.
- Добавить явные go:generate директивы с запуском закреплённого генератора через go tool minimock; генерировать только выбранные интерфейсы. Использовать -g, чтобы генератор не добавлял конкурирующие директивы с вызовом бинарника из PATH.
- Хранить моки рядом с unit-тестами как *_mock_test.go, коммитить их, вручную не редактировать. minimock поддерживает генерацию из интерфейсов и интеграцию с testing: [документация](https://github.com/gojuno/minimock).
- В CI выполнять go generate ./... и проверять, что нет изменённых или новых неотслеживаемых сгенерированных файлов. Устаревшие моки должны ломать проверку.
- Unit-тесты: go test -count=1 -coverprofile=coverage-unit.out ./.... Для отчёта: go tool cover -func=coverage-unit.out и go tool cover -html=coverage-unit.out.
- Тесты реальных адаптеров отметить build tag integration; отдельный обязательный CI-шаг go test -count=1 -tags=integration ./... запускает их вместе с unit-тестами.
- Отдельно запускать race detector в поддерживаемой CI-среде. Unit-тестам не нужны сеть, Spotify-аккаунт, реальный keyring или установленный терминал.

Предлагаемый порог CI — минимум 80% statement coverage отдельно для internal/syncer и internal/download, без сгенерированных моков. Уточнить список пакетов после реализации структуры. Порог не заменяет матрицу сценариев: все критические ветки дедупликации, повторного запуска и восстановления должны иметь тесты даже при уже достигнутом проценте. Покрытие адаптеров оценивать отдельно интеграционными тестами; не повышать его искусственно мокированием SQL.

Интеграционные проверки обязательны: minimock не доказывает корректность UNIQUE-ограничений, транзакций, реального rename, JSON-схемы Spotify или HTTP-пагинации. Для них использовать реальную SQLite в t.TempDir, файловую систему и httptest. Повторный end-to-end запуск должен подтвердить нулевое число HTTP-загрузок аудио.

## Проверка MVP

Автоматические сценарии используют httptest и собственные короткие аудиофайлы, без Spotify-аккаунта в CI.

| Сценарий | Ожидаемый результат |
|---|---|
| 100 вхождений, 80 уникальных сопоставленных источников | 80 загрузок; исходные позиции плейлистов сохранены |
| Повторный запуск без изменений | 0 запросов скачивания аудио; запросы метаданных допустимы |
| Добавлены три новых уникальных источника | Ровно три загрузки |
| Один трек в трёх плейлистах | Один файл, три ссылки |
| Разные source_id возвращают одни байты | После проверки один физический файл |
| Один ISRC, разные версии | Не объединяются без подтверждения |
| Файл удалён локально | Заново загружается только отсутствующий |
| Ошибка страницы каталога | Предыдущий полный состав сохраняется |
| 429, 401, 403, 404, 5xx | Ограниченные повторы; refresh при 401, понятные причины постоянных ошибок |
| QUOTA_EXCEEDED | Нет бесконечного цикла повторов |
| Обрыв загрузки или неверный хеш | Нет статуса done и готового повреждённого файла |
| Сбой после rename до записи done | При запуске файл найден и привязан без повторной передачи |
| Второй процесс синхронизации | Не создаёт параллельную задачу на тот же источник |
| Кириллица, длинные имена, закрытый файл антивирусом | Ошибка обрабатывается; БД и файлы остаются согласованными |
| Ctrl+C и resize терминала | Корректное завершение и отзывчивый TUI |

Команды приёмки после реализации: go test ./..., go vet ./..., go mod verify, govulncheck ./..., go build .. Race detector запускать в поддерживаемой среде с нужным C toolchain, например Linux CI.

Ручная приёмка: реальный вход Spotify, выбор одного плейлиста и тестовых разрешённых ссылок, запуск → повторный запуск → добавление трека → искусственный обрыв → восстановление. Успех: счётчики и HTTP-запросы подтверждают отсутствие повторной загрузки готовых файлов.

## Что решить перед адаптером реального каталога

Выбрать сервис/хранилище аудио и проверить право и техническую возможность получения файлов, наличие API поиска, покрытие коллекции, формат и качество. Прямые ссылки пригодны для проверки механики; они не обеспечивают автоматическое нахождение каждого Spotify-трека. Отсутствующие совпадения должны оставаться видимыми в TUI.
